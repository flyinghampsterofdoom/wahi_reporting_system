1. Management workflow
Recipe Builder uses a searchable library, independently scrolling canvas and live bartender
preview. Search existing recipe titles, click or drag to import stored ingredients/quantities,
author preparation, arrange components, upload a photo, preview, save draft and explicitly
publish. No historical preparation has been reconstructed. Missing instructions do not block
source import; publication still validates newly authored preparation/garnish/glassware.

Source snapshots retain recipe/revision/ingredient IDs, names, quantities, units, notes, yield,
and nested recipe references. Edits are independent service data. Search covers the existing
source catalog via SELECT-only endpoints; it does not depend on preparation being present.
The approved inventory of 186 source recipes is not copied into testing or rewritten. Browser
and backend acceptance use disposable, clearly synthetic sources without preparation.

Canvas fields support visible titles, ingredient names/quantities/units/notes, preparation,
garnish, glassware, service notes and yield. Add/remove lines and blocks, expand/collapse nested
recipes, insert library blocks into a chosen nested destination, and drag between positions.
Move up/down buttons are accessible keyboard alternatives; focus follows a reordered block.
Library items can also be inserted by clicking. Management may save selected blocks as reusable
common ingredients, preparation actions, garnishes, glassware or house mixes. Insertions receive
new component/item IDs and remain independent editable snapshots. Common-item examples are
explicitly selected templates, never inferred instructions for existing source recipes.

Save Draft persists without publishing. Publish confirms intent, saves/validates the draft,
and creates a new immutable publication with optimistic concurrency checks. Stale edits remain
visible until the user explicitly reloads. Menu classification changes independently. Duplicate
creates a private draft with no publication. Admin may archive/restore service entries and
recover historical publications into a draft; Manager cannot archive or recover. No operation
calls costing revision selection, cost basis, inventory mapping or Toast mutation.

3. Photographs and access
PrivateLocalRecipeMedia is an explicitly local-only adapter. Set WAHI_RECIPE_MEDIA_ROOT to a
private local directory when starting backend/review/server.js against a local development DB.
No storage is selected automatically. Hosted servers reject this adapter. A production storage
and retention/backup configuration still needs separate review and authorization before release.
No external provider or paid service was added. Sharp 0.35.5 is pinned in backend dependencies.

Upload is management-only, same-origin and CSRF protected. JSON/base64 transport has a dedicated
12 MiB request ceiling; ordinary JSON endpoints retain their 128000-byte limit. Decoded uploads
must be <=8 MiB, JPEG/PNG/WebP with matching actual MIME/format, valid fully decoded content,
<=24 million pixels and a single frame. Malformed, truncated, spoofed, oversized and animated
images are rejected. EXIF orientation is normalized; display metadata is stripped. Display
WebP derivatives fit inside 1400x1600 without cropping or enlargement, quality 82.

Originals and derivatives use random immutable object IDs, private directory permissions 0700
and file permissions 0600. Originals are never served by HTTP/static assets. Display delivery
checks integrity and database authorization and uses no-store/nosniff. Staged/draft photos are
management-only and checked against the entry/current draft. Station access is limited to the
active current approved published image; management may retrieve historical published images.

Preview-before-save uses device-local blob URLs. Save uploads to the selected entry and stores
the returned media reference in the service draft. Replace/remove modifies draft references
only. Publication stores its own immutable photo ID. There is no deletion/GC endpoint: historical
originals/derivatives remain available. Migration 032 prevents media content/identity mutation
or deletion while still allowing approval revocation. Failed DB writes after filesystem storage
may leave unreferenced private objects; they are retained for reviewed reconciliation, never
automatically deleted. Backup/retention operations are outside this local implementation.
A missing photo is a visible content warning and never a publication blocker.
