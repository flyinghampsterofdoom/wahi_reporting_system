Specific root cause
An application-version consistency gap in long-lived tabs. The old renderer remained in memory across a server deployment. Recipe Book Refresh and its 30-second refresh timer fetch current published documents but do not replace the renderer or check the loaded bundle version. Hash navigation between Builder and Book also retains that JavaScript context.
This is not an inference based solely on the word “cache”. The old script URL and old render function were inspected directly, with current instruction-bearing data present in the same failing session. A fresh screenshot did not correspond to a new document load.
There is no evidence that the service worker delivered an obsolete document on the owner's reload. The observed tab loaded before deployment; the ordinary reload immediately loaded the correct production rendering without clearing browser caches or storage.

Deployment, API and path investigation
Render still reports deployment dep-dbcdob0n74is73877db0 / commit daed179 live. Public HTML references the corrected renderer, and fetched renderer/foundation/builder/worker bytes match that commit.
The published API returns 151 Swizzle's six ingredient rows, four preparation instructions, garnish and glassware. Its saved publication and draft contain those instructions. There is no missing-data repair to perform.
Book selection, Book data refresh, menu filtering and full-size builder preview all use the shared WahiRecipeRenderer. There is no alternate role-specific renderer for On Menu. The old and new implementations coexisted in separate browser documents, not as a menu-status branch in the deployed code.
The repository's legacy /recipe-books application is separate from the deployed /#recipe-book route and did not produce this screen.
Menu status filters membership in the recipe list; it does not change a recipe document or the renderer. Publication state does not explain the stale arrows: the current published document was already present in the failing tab.

Why the previous acceptance test passed
The prior production test launched a new isolated Chromium context, injected the authorized owner session and navigated to /#recipe-book AFTER deployment. That correctly downloaded dc7c39497f3b209e and passed the visible assertions. The account permissions and route matched; the browser document lifetime did not.
That test covered the then-published 151 Swizzle via All (it was Off Menu at the time). The owner subsequently published/classified additional recipes, bringing the current On Menu count to 23. Those membership changes do not select a different render path.
The test did NOT preserve a pre-deployment application document across deployment, then use its data-only Refresh. It therefore missed the actual warm-session failure. Earlier local comparison screenshots also deliberately disabled service-worker interception to choose before/after assets deterministically; those were not an upgrade-lifecycle test.
The earlier report was accurate for a fresh session but incomplete as a guarantee for existing sessions.

Local preventive correction — NOT DEPLOYED
- server.js publishes a no-store application-version manifest derived from asset fingerprints and the release identity, and embeds the matching version in HTML.
- app-version.js checks that version on focus, visibility/online changes, navigation, Book Refresh and a 30-second interval. A clean Book reloads after a version mismatch. Dirty/parked Builder drafts and other working pages get an update notice; dirty Builder drafts cannot be discarded by its reload button. A session marker prevents repeated automatic reloads for the same target version.
- The new bootstrap script participates in the existing fingerprinted assets and offline shell dependency set. Authentication, offline leases and account-scoped cached recipe data are unchanged.
- The all-content-bearing-block requirement also exposed a separate blanket omission of notes-type instructions in the current projection/renderer. The local patch includes saved note text as service-note sections, rather than discarding every notes block by type. This was not the cause of 151 Swizzle's reported discrepancy, whose publication has no notes block. No saved note or recipe text was edited.
- The renderer continues to omit underlying child recipe formulas while retaining those relationships in the saved graph and management editor. No name-specific logic or 151 Swizzle workaround is introduced.

Preservation and current status
No production recipe mutation requests were performed by the verification script; all non-GET Recipe Book requests were blocked there. Production SQL access used default_transaction_read_only=on. Native UI actions inspected diagnostics, expanded one obsolete disclosure for reproduction, and reloaded a clean Book; no save/publish controls were used.
The saved 151 Swizzle draft, publication identity, content and source relationships match the initial investigation snapshot. Source/costing/inventory/history write paths, contracts, migration files and Builder editing code are unchanged. Existing isolation/history/costing regressions pass; disposable test databases were removed.
Production remains daed179. Other legacy documents opened before that deployment need one normal reload. The new version guard can prevent recurrence after its own initial rollout, but cannot execute inside an already-loaded legacy document until that document reloads.
